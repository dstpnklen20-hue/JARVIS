# Джарвис — правила для Claude Code

**В начале каждой сессии прочитай `docs/HANDOFF.md`** — где мы остановились, что сделано, что
дальше и как мы работаем. В конце сессии (или когда пользователь просит сохранить итоги) —
обнови его.

Полное ТЗ: `JARVIS_SPEC.md`. Здесь — выжимка разделов 0, 2 и 10, обязательная в каждой сессии.
Общение с пользователем — на русском.

## Как работать (раздел 0)

- Приоритеты: **скорость реакции → качество распознавания → надёжность** (без падений, зависаний, утечек).
- Работать **строго по этапам** (раздел 11 ТЗ). Перед этапом — план и «ок» пользователя.
  Не делать несколько этапов разом и не переходить к следующему без подтверждения.
- После этапа: `cargo test`, `cargo clippy --all-targets -- -D warnings`, `cargo fmt --all --check`,
  затем отчёт: что сделано; как проверить руками (шаги и фразы); замеры задержек; ограничения.
- **Не выдумывать API.** Перед использованием крейта проверить актуальную версию и документацию
  (docs.rs), что крейт не заброшен; при сомнении — маленький проверочный пример.
  Версии закреплять в `Cargo.toml`, `Cargo.lock` коммитить.
- Не переписывать работающий код без причины. Маленькие изменения, понятные коммиты.
  Коммитить и пушить — только по просьбе пользователя (remote: github.com/dstpnklen20-hue/JARVIS).
- Неоднозначно — спросить, не угадывать. Новый тип действия — сначала описать пользователю.

## Модель разрешений (раздел 2)

- Действие, которое пользователь ещё не разрешил, выполняется **только после ответа**:
  «да» — один раз; «всегда» — запомнить; «нет» — не выполнять; «никогда» — запомнить запрет;
  тишина 10 с — не выполнять. Параллельно — уведомление с кнопками. Вопрос называет, что именно произойдёт.
- Разрешения — только в `config/permissions.toml`, **не в манифестах**: чужой пакет не может выдать себе
  разрешение. Привязка к `id` команды и хешу её действия: действие изменилось — спросить снова.
- `always_ask = true` в манифесте — «всегда» не предлагается (пользователь может снять в permissions.toml).
- Игровой режим: одно разрешение на весь профиль при его включении.
- Надёжность:
  - распознанный текст **никогда не исполняется как код** — речь только выбирает описанную команду;
    параметры из речи — слоты с типом и проверкой (число в диапазоне / значение из списка);
  - процессы — `std::process::Command` со списком аргументов, без строки оболочки, всегда с таймаутом;
  - сбой команды не роняет и не вешает ядро: лог + «Не удалось, сэр»;
  - аварийная остановка (горячая клавиша и «Джарвис, стоп»): отпустить клавиши, завершить скрипт,
    выйти из игрового режима, пауза;
  - журнал действий с ротацией (время, текст, команда, уверенность, разрешение и как получено, результат);
  - секреты — только в keyring ОС, никогда в коде, конфигах, логах;
  - аудио на диск не пишется по умолчанию;
  - запуск от администратора — предупредить один раз, но работать.

## Качество кода (раздел 10)

- Rust stable. `unsafe_code = "deny"` во всём workspace, кроме `jarvis-platform`:
  там `unsafe` только для вызовов WinAPI, минимальными блоками, каждый с `// SAFETY:`.
- `clippy -D warnings`, `rustfmt`. Ошибки: `thiserror` в библиотеках, `anyhow` в бинарниках.
  **Никаких `unwrap()` / `expect()` в рабочем коде** (в тестах можно; clippy это проверяет).
  Паника в потоке не роняет приложение.
- Типы ошибок не повторяют причину в своём тексте — она отдаётся через `source()`;
  для показа человеку — `jarvis_core::error_chain`.
- Логи — `tracing` с уровнями и компонентами; журнал действий — отдельно.
- Аудио-callback никогда не блокируется и не аллоцирует (lock-free кольцевой буфер).
- Тесты обязательны: автомат состояний (все переходы), разрешения (да/всегда/нет/никогда/тишина,
  always_ask, смена действия, чужой пакет), манифесты (валидные, невалидные, дубли, неизвестные поля),
  нормализация и сопоставление, исполнители (подмена системных вызовов через трейты),
  аудиоконвейер на WAV из `tests/fixtures/`.
- Корректное завершение (потоки, микрофон, отпускание клавиш), защита от второй копии.

## Режим работы (с 2026-10-12)

Пользователь теперь участвует: проверяет вживую и присылает замечания — их исправлять в первую
очередь. Решения по своим рекомендациям принимать можно; личное (git push, образец голоса, ключи,
системные настройки) — не трогать, вынести в «Ждёт вас». Голос и звук оценивает пользователь на
слух (локальные страницы прослушивания в `tools/voice/`), а не метрики. **После каждого этапа
дополнять `docs/DEVELOPMENT.md`** (что сделано, решения с обоснованием, замеры) и `docs/HANDOFF.md`.

## Практика проекта

- Стек слуха — sherpa-onnx (вместо rustpotter/vosk/webrtc-vad из ТЗ; обоснование в `docs/DEVELOPMENT.md`).
  Перед первой сборкой — `scripts/download-models.ps1` (архив библиотеки sherpa-onnx берётся оттуда).
- Тесты на моделях — `#[ignore]`; полный прогон: `cargo test --release -- --include-ignored`.
- Сборка в этой среде: `$env:Path = "$env:USERPROFILE\.cargo\bin;$env:Path"` (если cargo не в PATH).
- Не читать/писать UTF-8 файлы через `Get-Content`/`Set-Content` Windows PowerShell 5.1 — портят кириллицу.
  `.ps1` со строками на русском сохранять в UTF-8 **с BOM**.
- Ресурсы (модели, libvosk) описаны в `scripts/assets.json` — единый источник для скрипта и `jarvis --check`.
